# Решения прототипа

## Реализация и данные для оценки

Валидатор реализован на Python. CLI использует OpenAI SDK для вызовов модели, Pydantic для проверки структуры ответов и pypdf для чтения PDF.

Разметка `evaluation/gold.json` написана по документу организатора и исключена из Docker-образа и входа модели. Исходный Markdown сохранён в тестовых фикстурах как документ организатора. [Документ по коммиту](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md)

## Движок и объём проверки

- Детерминированная нарезка сначала выделяет адресуемые блоки. Документ сохраняет исходные ID и строки, а PDF ещё и страницы. Примеры и служебные фрагменты доступны для доказательств, но в реестр требований не входят. Служебные пустоты анализируются на уровне полноты документа.
- Каждый локальный пакет получает исходный контекст целиком. Отдельный проход оценивает весь набор и четыре требуемые межраздельные связи. Модель обязана вернуть полный набор статусов. Если возвращены не все ID или критерии, движок просит повторить ответ. При превышении бюджета до модели документ не обрезается и агент сообщает об ограничении.
- Осмысленность находки оценивает модель, буквальную опору проверяет код. Нормализуются только пробельные символы, сравнение регистрозависимое. JSON хранит исходную цитату и координаты после проверки. Для конфликта требуются две неперекрывающиеся опоры и сценарий. Неполное покрытие означает ошибку этапа или потерю части текста при импорте. Неопределённые оценки перепроверяются отдельно и выводятся как вопросы к аналитику.
- Повторы ищутся по координатам, ID, рубрике и близости формулировок. Модель может объединить лишь заранее предложенную согласованную пару, независимые опоры остаются, а вложенные цитаты одного блока удаляются. Дублирующее правило в самом ТЗ выделяется как отдельный тип дефекта при риске расхождения. Сортировка и итог о готовности выполняются кодом.
- PDF читается через pypdf с текстовым слоем. Координаты относятся к извлечённым строкам внутри страниц. Скан нужно распознать заранее. Сложные колонки, объединённые ячейки и разрывы таблиц требуют проверки качества извлечения. DOCX поддерживает верхнеуровневые абзацы и таблицы в порядке документа.
- Ядро не зависит от файловой записи CLI. Веб-обёртка сможет передать документ и провайдер в `ReviewEngine` и отрендерить результат. JSON хранит то же ревью для оценки и потенциального UI. PDF требуется как вход, обязательный выход — Markdown.

Шрифт для русского PDF берётся из системы или передаётся вручную, файл шрифта в набор не включён. Выбран pypdf, чтобы не добавлять PyMuPDF с AGPL или коммерческой лицензией. [pypdf, извлечение текста](https://pypdf.readthedocs.io/en/stable/user/extract-text.html) · [PyMuPDF, лицензирование](https://pymupdf.io/licensing)

Для прямого OpenAI применяется Responses API с Pydantic Structured Outputs. Протокольные настройки Gemini изолированы в Chat Completions. У Responses нет seed. У reasoning-моделей температура и предел выхода зависят от модели, поэтому дополнительные параметры передаются только из конфигурации. У OpenAI задано `store=False`. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) · [Reasoning](https://developers.openai.com/api/docs/guides/reasoning) · [Совместимость Gemini](https://ai.google.dev/gemini-api/docs/openai)
