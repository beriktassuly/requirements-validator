### D-001 — Описанная операция одновременно назначена для чтения и замены настройки

- Уровень — Критический
- Критерии — Согласованность, Однозначность, Полнота
- Обнаружено при проверке — отдельное требование, набор
- Требования — B019, B035, B068, B069, B073, B084, B098, B099, B106

Описание называет чтение функциональным назначением метода, но алгоритм метода требует заменить настройку. Метод и пример запроса не разделяют эти действия, поэтому нельзя однозначно реализовать загрузку и сохранение настроек.

**Сценарий.** При открытии экрана приложение хочет прочитать сохранённый порог 30 000 ₸. Если оно вызывает единственную описанную операцию с обязательным amount=50000, чтение должно оставить 30 000 ₸, тогда как алгоритм заменяет значение на 50 000 ₸. Без amount запрос не соответствует описанному контракту.

**Исправление.** Разделить контракты чтения без изменения состояния и записи. Для каждого указать метод, путь, входные параметры, ответ и эффект; согласовать описание, алгоритм и примеры. Для записи выбрать метод, предназначенный для изменения ресурса.

<details><summary>Дополнительные формулировки исправления</summary>

- Зафиксировать операцию чтения без изменения настройки и указать, как её ответ заполняет порог и переключатель для карты с сохранённой настройкой и без неё.
- Добавить контракт чтения без изменения состояния: метод и путь, идентификатор карты, ответ с текущими настройками и результат при отсутствии сохранённой настройки. Отдельно обозначить назначение операции сохранения.

</details>

### D-002 — Для отклонённой суммы пример под HTTP 200 расходится с правилами статусов

- Уровень — Критический
- Критерии — Согласованность
- Обнаружено при проверке — отдельное требование, набор
- Требования — B024, B035, B083, B085, B098, B104, B111, B112

B111 и B104 относят HTTP 200 к успеху, а B112 относит неверные параметры к HTTP 400. При этом раздел примеров для HTTP 200 допускает альтернативное тело с `result: ERROR` и сообщением о сумме. ### D-003 — Правило и приёмка относят покупку к разным месяцам

- Уровень — Критический
- Критерии — Согласованность
- Обнаружено при проверке — отдельное требование, набор
- Требования — B025, B042

B025 относит проведённую покупку к месяцу её совершения, а B042 требует увеличить счётчик месяца проведения. Для покупки на границе месяцев нельзя одновременно реализовать правило учёта и пройти приёмку.

**Сценарий.** Покупка на 4 000 ₸ совершена 31 января в 23:58 и проведена 1 февраля в 00:03 по времени Алматы. B025 требует увеличить январский счётчик, B042 — февральский.

**Исправление.** Выбрать дату, определяющую месяц учёта: совершение или проведение в часовом поясе Алматы. Согласовать с этим выбором B025 и ожидаемый результат B042.

<details><summary>Дополнительные формулировки исправления</summary>

- Зафиксировать единственный источник даты для выбора месяца в Алматы и привести критерий приёмки в соответствие. Отдельно указать, что проведение определяет момент включения покупки в учёт, если именно это задумано.

### D-004 — Не определён приоритет месячного лимита push над сменой порога

- Уровень — Критический
- Критерии — Согласованность
- Обнаружено при проверке — отдельное требование, набор

Ф-3 запрещает второй push по карте за месяц, а Ф-4 требует push при следующем достижении нового порога независимо от истории. Для основного сценария после изменения настройки нет единственного допустимого результата.

**Исправление.** Заменить «и далее» точным перечнем кодов либо явным указанием классов 4xx и 5xx, в зависимости от принятого контракта.

**Доказательства**

- B104, страница PDF 3, строка 150, символы 40–84

```text
Если результат 400, 401 и далее — неуспешный.
```

- B119, страница PDF 4, строка 175, символы 1–66

```text
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.
```

<a id="d-056"></a>
### D-056 — Пример 500 не определяет обязательные поля ответа

- Уровень — Незначительный
- Критерии — Полнота
- Обнаружено при проверке — отдельное требование
- Требования — B106, B119

B119 задаёт код 500, а пример содержит только `message`. Общая таблица также описывает `result` со значением `ERROR`, но применимость этого поля к внутреннему сбою не указана. Тестировщик не может определить, соответствует ли контракту ответ 500 без `result`.

**Сценарий.** Хранилище настроек выдаёт внутренний сбой, и метод возвращает HTTP 500 с телом из примера. Код проверяем, но обязательность поля `result` не определена.

**Исправление.** Зафиксировать обязательные поля ответа 500 и явно указать, должен ли он содержать `result: ERROR`; привести пример в соответствие с этим правилом.

**Доказательства**

- B106, страница PDF 3, строка 154, символы 1–57

```text
| `result` | string | OK / ERROR | Исход сохранения | — |
```

- B119, страница PDF 4, строка 175, символы 1–66

```text
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.
```

- B129, страница PDF 4, строка 196, символы 1–28

```text
{"message":"Ошибка сервиса"}
```

<a id="d-057"></a>
### D-057 — Неясно, обязательны ли точные тексты сообщений из примеров

- Уровень — Незначительный
- Критерии — Однозначность
- Обнаружено при проверке — отдельное требование
- Требования — B109

Таблица определяет `message` как строковое описание ошибки, а примеры приводят конкретные формулировки. Не указано, являются ли они частью контракта. Из-за этого тестировщик может требовать точного совпадения там, где разработчик считает допустимым другой текст с тем же смыслом.

**Сценарий.** При отсутствии авторизации сервис возвращает «Войдите в приложение» вместо «Требуется вход». Тип и назначение поля соблюдены, но неясно, должен ли тест принять другой текст.

**Исправление.** Пометить тексты сообщений в примерах как иллюстративные либо перечислить обязательные формулировки для соответствующих ошибок.

**Доказательства**

- B109, страница PDF 3, строка 157, символы 1–57

```text
| `message` | string | При ошибке | Описание ошибки | — |
```

- B123, страница PDF 4, строка 184, символы 1–28

```text
{"message":"Требуется вход"}
```

<a id="d-058"></a>
### D-058 — Ответ 404 описан в подразделе ответа 403

- Уровень — Незначительный
- Критерии — Согласованность
- Обнаружено при проверке — отдельное требование
- Требования — B125

Подраздел маркирует описываемый ответ как 403, тогда как B125 и метка примера указывают 404. Это расхождение видно даже для отсутствующей карты, независимо от трактовки запрета доступа в B118. При переносе примера в описание API или в тест по заголовку ему могут присвоить неверный статус.

**Сценарий.** Авторизованный клиент передаёт корректный идентификатор отсутствующей карты. По B125 ожидается 404, но при привязке ответа к коду подраздела он будет описан как 403.

**Исправление.** Перенести B125 и его пример в отдельный подраздел 404, не меняя установленный код ответа.

**Доказательства**

- B124, страница PDF 4, строка 187, символы 1–34

```text
#### 403. Unsuccessful — Forbidden
```

- B125, страница PDF 4, строка 188, символы 1–64

```text
Для чужой карты возвращается 404, как и для отсутствующей карты.
```

- B126, страница PDF 4, строка 189, символы 1–7

```text
**404**
```

## Приоритет исправлений

1. [D-001](#d-001) (критический) — Разделить контракты чтения без изменения состояния и записи. Для каждого указать метод, путь, входные параметры, ответ и эффект; согласовать описание, алгоритм и примеры. Для записи выбрать метод, предназначенный для изменения ресурса.
2. [D-002](#d-002) (критический) — Закрепить одну пару HTTP-статуса и результата для отклонённой суммы. Если отклонение считается ошибкой параметра, перенести пример с `ERROR` в раздел HTTP 400 и согласовать его тело со схемой ответа.
3. [D-003](#d-003) (критический) — Выбрать дату, определяющую месяц учёта: совершение или проведение в часовом поясе Алматы. Согласовать с этим выбором B025 и ожидаемый результат B042.
4. [D-004](#d-004) (критический) — Указать, сбрасывает ли смена порога право на push. Если месячный максимум абсолютен, явно подчинить ему Ф-4; если предусмотрено исключение, изменить Ф-3 и описать его границы.
5. [D-005](#d-005) (существенный) — Описать ответ чтения для карты без сохранённой настройки, включая представление отсутствующего порога, и указать поле или отдельный интерфейс для фактического месячного итога с форматом и единицей измерения.
6. [D-006](#d-006) (существенный) — Указать, за какой календарный месяц и по какой карте показывается сумма, и связать её с тем же счётчиком, который используется при сравнении с порогом.
7. [D-007](#d-007) (существенный) — Явно распространить отсутствие записи на все ошибки валидации, включая отсутствие и недопустимое значение enabled, и задать машиночитаемый способ определить поле с ошибкой либо правило локальной проверки на клиенте.
8. [D-008](#d-008) (существенный) — Добавить отдельный вход для события возврата либо ссылку на процесс его обработки; указать, где обновляется счётчик месяца исходной покупки и как завершается эта ветка.
